# Code-Duplication Report Formats

Status: research note (Wayfinder ticket 07). Does **not** select a report format — it collects evidence for that decision.

Scope: machine-readable report formats for code-duplication *candidates* — results where each record needs **two or more source spans** (the locations that duplicate each other), a **similarity score**, the **source language**, and **node-count/token-count/line-count** metadata. Compared SARIF 2.1.0 (OASIS), PMD CPD's native formats, jscpd's JSON/SARIF/Code-Climate reporters, and the Code Climate/GitLab "Code Quality" issue spec, all against primary sources (specs, schemas, and reporter/engine source, not secondary write-ups). Also verifies, from poly-crap's own source and docs, whether poly-crap already emits a relevant duplication-report format.

## 0. Does poly-crap already emit a duplication-report format? No

poly-crap (`D:\Personal\poly-crap`) is a Rust CLI that reports **cyclomatic complexity + coverage ("CRAP score")**, not code duplication, and nothing in its formats models a duplication candidate:

- `--format sarif` writes **one SARIF result per function over the CRAP threshold**, under rule `poly-crap/crap-threshold` (`docs/content/05-output/01-machine-formats.mdx`). The renderer (`src/report.rs`, `render_sarif`, ~lines 673-705) gives each result **exactly one** `locations[]` entry — one `physicalLocation` (`artifactLocation.uri` + `region.startLine`/`endLine`) — with no `relatedLocations`, no `codeFlows`, and no `properties` bag.
- `--format json` validates against `schemas/report-v1.json` / `schemas/delta-v1.json`: both model **one code unit per entry** (`language`, `file`, `symbol`, `start_line`, `end_line`, `complexity`, `coverage`, `coverage_basis`, `score`, …) — a single span, not a pair/group of spans.
- A search of poly-crap's Rust source (`src/*.rs`) and both schemas for `similarity`/`duplicate`/`clone` turns up only ordinary Rust `.clone()`/`#[derive(Clone)]` usage and a `git_diff.rs` test fixture string containing the literal text `similarity index 80%` (a `git diff --find-renames` artifact, unrelated to clone detection) — no duplication-domain field exists anywhere.

**Conclusion:** poly-crap demonstrates that a Rust CLI can validly emit SARIF 2.1.0 and a versioned custom JSON schema — a useful engineering precedent for poly-dry's output plumbing — but it is **not** an example of a 2+-span/similarity-score duplication format and contributes no schema design for that shape.

## 2. SARIF 2.1.0 — detail

Primary sources: the OASIS-published JSON Schema at `https://json.schemastore.org/sarif-2.1.0.json`, and GitHub's documented SARIF ingestion rules.[^gh-sarif]

- **`result.locations`** is schema-legal as an array, and its own description recommends "only one location unless the problem... can only be corrected by making a change at every specified location" — but GitHub's docs state only the first array value is used and the rest are ignored.[^gh-sarif] Using `locations[]` with 2 entries to encode a duplication pair would therefore silently drop the second span for GitHub's code-scanning UI.
- **`result.relatedLocations`** is the correct, precedented mechanism for a second/Nth span: GitHub "will link to related locations when they are embedded in the result message."[^gh-sarif] jscpd's own SARIF reporter implements exactly this pattern — one primary `locations[0]` (fragment A), one `relatedLocations[0]` with `id: 0` (fragment B), and a `message.text` containing an embedded markdown-style link (`[text](0)`) referencing that id; jscpd's code comments state the embedded link is *required* for GitHub to surface the related location.[^jscpd-sarif]
- **`result.codeFlows`/`threadFlows`** are also multi-location-capable and GitHub-supported, but model *ordered* execution-path locations (classic taint source→sink use case). jscpd chose `relatedLocations` over `codeFlows` for duplication pairs, consistent with duplication being a symmetric pair/group relation rather than an ordered flow — both remain schema-legal options.
- **`result.properties`** (the generic property bag) is the sanctioned SARIF-spec extension point for anything SARIF lacks natively. jscpd's SARIF reporter places `token_count`, `similarity`, `similarity_method`, `nodes` (AST size), and `clone_hash` here — none are standard SARIF fields. Caveat: GitHub's own "Supported properties" table for the `result` object lists `ruleId`, `ruleIndex`, `rule`, `level`, `message.text`, `locations[]`, `partialFingerprints`, `codeFlows[].threadFlows[].locations[]`, and `relatedLocations[]`, but does **not** list `result.properties` or `result.rank` as a property GitHub code scanning reads — so a `properties` bag is portable to any spec-conformant SARIF consumer (and is how jscpd carries its data), but is not guaranteed to be displayed by GitHub's code-scanning UI specifically.[^gh-sarif]
- **No native similarity score.** `rank` (0-100) and `level` (none/note/warning/error) are the only severity-adjacent fields; jscpd's SARIF reporter does not use `rank` at all, deriving `level` from a severity heuristic instead of mapping similarity continuously — confirming SARIF needs `properties` for a genuine similarity score.[^jscpd-sarif]
- **No built-in "duplicate code" taxonomy.** jscpd defines its own five `reportingDescriptor` rule IDs (`jscpd/duplicate-code`, `jscpd/renamed-code`, `jscpd/similar-code`, `jscpd/similar-function`, `jscpd/semantic-code`) — a single-tool convention, not a cross-tool standard.[^jscpd-sarif]
- **`physicalLocation.region`** fields (`startLine`/`startColumn`/`endLine`/`endColumn`/`charOffset`/`charLength`/`byteOffset`/`byteLength`/`snippet`/`sourceLanguage`) map directly onto a single span with zero extension needed.
- **`partialFingerprints`** is the standard mechanism for cross-run result identity/dedup; jscpd stores a custom key (`jscpdCloneHash/v1`) inside it — the sanctioned way to extend a standard object rather than inventing a new top-level field.[^jscpd-sarif]
- **Scale limits relevant to portability:** GitHub caps SARIF ingestion at 25,000 results/run (top 5,000 kept by severity), 1,000 locations/result (100 displayed), 10,000 thread-flow locations/result (top 1,000 kept), and 10 MB max gzip file size.[^gh-sarif]

## 3. PMD CPD — detail

Primary source: `https://docs.pmd-code.org/latest/pmd_userdocs_cpd_report_formats.html` (the historical `pmd.github.io` doc path 404s; `docs.pmd-code.org` is the current canonical host) plus `pmd_userdocs_cpd.html` for the CLI/format overview.[^pmd-cpd]

- Native XML root `<pmd-cpd>` (XSD `https://pmd.github.io/schema/cpd-report_1_0_0.xsd`). Each match is a `<duplication lines="…" tokens="…">` containing **2 or more** `<file column="…" endcolumn="…" endline="…" line="…" begintoken="…" endtoken="…" path="…"/>` elements, plus one `<codefragment><![CDATA[...]]></codefragment>`.
- This is the only surveyed format that natively models an **N-ary** duplication group (3+ copies of the same fragment in a single record) instead of forcing a pairwise decomposition.
- Confirmed across all 6 CPD report formats (text, xml, csv, csv_with_linecount_per_file, vs, markdown): **no similarity-percentage field anywhere** — only `lines`/`tokens` counts and occurrence counts.
- `--language` is a single global CLI flag for the whole run; none of CPD's native formats carry a per-duplication language field, consistent with CPD being single-language-per-invocation.
- No property-bag/extension mechanism exists; adding a similarity score would require forking CPD's renderer or post-processing its XML output.
- Not independently fetched: the Java renderer source in `apache/pmd` (`pmd-core`) — findings here rely on the documented XML schema/examples, not the implementation itself.

## 4. jscpd (Rust engine) — detail

Primary sources: the Rust implementation files in `kucherenko/jscpd` (not just docs) — `rust/crates/cpd-reporter/src/json_reporter.rs` and `rust/crates/cpd-reporter/src/sarif.rs`, commit `0b519608c47d287f59018ce4ad7f9939ac93e0c8`.[^jscpd-json][^jscpd-sarif]

- **Currency note:** jscpd is no longer the classic Node.js tool; it is now a from-scratch Rust engine (`rust/crates/cpd-*`) exposing 224 language formats and Type-1/2/3/4 clone detection (exact/renamed/similar/semantic via `--similarity`/`--semantic`/`--max-gap-lines`), distributed as a self-contained binary while keeping legacy CLI flags/config for compatibility. The classic path `packages/jscpd/README.md` now 404s; current docs live at root `README.md`, `docs/rust.md`, `FORMATS.md`.
- **JSON reporter schema** (`duplicates[]`): `format` (language), `lines`, `fragment`, `tokens`, `firstFile`/`secondFile` (each: `name`, `start`, `end`, `startLoc`/`endLoc` with line/column/position, optional `nodes` for AST size, optional `blame`), `isNew`, `kind` (`exact`/`renamed`/`similar`/`semantic`), and — **conditionally** — `similarity` (float) + `method`, present only for `kind ∈ {similar, semantic}` (confirmed by an explicit test, `json_duplicate_includes_similarity_only_for_similar_clones`).[^jscpd-json] A universal 0-1 similarity field is *not* a given even in a tool built specifically for duplication: exact/renamed matches imply similarity 1.0 implicitly rather than encoding it.
- Structure is a strict **pair** (`firstFile`/`secondFile`), not CPD's N-ary group; a fragment duplicated 3+ times is presumed — not explicitly confirmed from the clustering/engine core — to be emitted as multiple pairwise `duplicates[]` entries.
- **SARIF reporter** confirms the `locations[0]` + `relatedLocations[0]` + embedded-markdown-link pattern (§2), the custom 5-rule taxonomy, and `properties`-bag usage for `token_count`/`similarity`/`similarity_method`/`nodes`/`clone_hash` — a concrete, working precedent for exactly the SARIF extension poly-dry would need.[^jscpd-sarif]
- jscpd also emits Code Climate/GitLab Code Quality JSON directly (`codeclimate.rs`), which is the real-world evidence behind §5.[^jscpd-cc]

## 5. Code Climate / GitLab Code Quality — detail

Primary sources: `codeclimate/platform` `spec/analyzers/SPEC.md` (canonical "Issue" schema)[^cc-spec] and jscpd's `rust/crates/cpd-reporter/src/codeclimate.rs` (a real, tested implementation targeting GitLab's narrower "Code Quality report" convention, output file `gl-code-quality-report.json`, consumed via `artifacts:reports:codequality` in GitLab CI).[^jscpd-cc]

- Canonical Issue fields per `SPEC.md`: `type` (always `"issue"`), `check_name`, `description`, `content` (optional), `categories` (required, ≥1), `location` (required `Location`), `other_locations: [Location]` (appears in the spec's worked JSON example) **but** the itemized field list instead documents a `trace` field (a `Trace` object, "other interesting source code locations related to this issue") — an unresolved inconsistency in the primary spec itself, reported as-is.[^cc-spec]
- Also defined: `remediation_points` (optional effort estimate), `severity` (`info`/`minor`/`major`/`critical`/`blocker`), `fingerprint` (cross-run identity, optional).
- **jscpd's mapping** (targeting GitLab's variant specifically, per its own code comment citing GitLab's Code Quality report docs): each clone pair produces **two** Issues (one anchored at fragment A describing fragment B, and vice versa); `location` = anchor span (`path`, `lines.begin`/`lines.end`); `other_locations` = `[location-of-the-other-span]`; `check_name` reuses the SARIF rule ids; `severity` = `"major"` if new-vs-baseline or over a duplication threshold, else `"minor"` — **no numeric similarity field is carried into the output at all**; size is only conveyed as free text inside `description`.[^jscpd-cc]
- jscpd's own code comment notes the secondary span is present in the file but not rendered by GitLab's merge-request UI, only recoverable by other tooling reading the raw JSON.[^jscpd-cc]
- No node/token-count structured field, no per-duplication language field, no property-bag extension point; additional metadata can only go into free-text `description`/`content` or be omitted.

## 6. What maps directly vs. what needs a custom property

- **Maps directly, no extension needed, in at least one surveyed format:**
  - 2+ spans per result — PMD CPD (N-ary, native) and Code Climate/GitLab (pairwise, native via `other_locations`).
  - Size/node-count — PMD CPD (`lines`/`tokens`) and jscpd JSON (`tokens`/`lines`/optional `nodes`).
  - Language — jscpd JSON (`format` field, per match).
  - Single-span region detail (line/column/offset) — SARIF `physicalLocation.region`.
- **Requires a custom/vendor property in every surveyed format:**
  - A continuous similarity score has **no standard home** in SARIF (needs `properties`), PMD CPD (no mechanism at all), or Code Climate/GitLab (no field; jscpd drops it into `severity`/`check_name` instead of carrying the number). Only jscpd's own JSON carries a true numeric similarity, and only conditionally (`similar`/`semantic` kinds).
  - A second-or-further span in SARIF requires `relatedLocations` (works, GitHub-supported) rather than `locations[1+]` (schema-legal but silently truncated by GitHub).
  - A per-result language field in SARIF or Code Climate/GitLab requires a custom `properties`/free-text workaround; neither has a native field.

## 7. Portability and consumer-tooling trade-offs

- **SARIF** is the only *formal, cross-ecosystem* standard surveyed (OASIS, versioned, broad adoption: GitHub, GitLab, Azure DevOps, many SAST tools) — the strongest portability story — but it has no native duplication/similarity semantics, so a poly-dry SARIF report would depend entirely on the `properties` bag plus the `relatedLocations` convention jscpd already validates in production, and on documented platform limits (result/location/file-size caps) that matter at scale.[^gh-sarif]
- **PMD CPD's** XML is the only format that natively avoids pairwise decomposition for 3+-way duplicates, but it is a single-tool, non-standard, duplication-only format with no consumer base outside PMD's own plugin ecosystem and no path to a similarity score without forking its renderer.[^pmd-cpd]
- **jscpd's** own JSON is the most duplication-native of the four (language, size, conditional similarity, pair spans) but is tied to one actively-evolving, recently-rewritten tool, and is not independently standardized — anyone consuming it couples to jscpd's schema stability, which has already changed significantly across its Node.js→Rust transition.[^jscpd-json]
- **Code Climate/GitLab Code Quality** buys GitLab-native CI integration for free, but the spec itself is ambiguous (`other_locations` vs. `trace`) and GitLab's own UI does not render the second span even when present — i.e. the "2+ spans" capability is real in the file format but not surfaced by the primary consumer.[^cc-spec][^jscpd-cc]
- A practical, already-field-tested pattern (demonstrated by jscpd) is to **emit more than one format from the same engine** — e.g. SARIF (for GitHub/editor integration) plus a tool-native JSON (that fully and losslessly captures 2+ spans, similarity, language, and node counts) — rather than forcing one format to do both jobs.[^jscpd-sarif][^jscpd-json][^jscpd-cc]

## 8. Gaps and uncertainties

- OASIS SARIF spec section numbers (e.g., "§3.27 result object") were not independently pinned against the numbered HTML spec at `docs.oasis-open.org`; findings instead cite the companion JSON Schema (`json.schemastore.org/sarif-2.1.0.json`) and GitHub's SARIF-support docs, both authoritative but not the numbered OASIS HTML text itself.
- jscpd's handling of a fragment duplicated 3+ times is inferred (strict `firstFile`/`secondFile` pair shape in the reporter structs) rather than confirmed by reading the clustering/engine core that groups matches.
- PMD CPD's actual Java renderer source (`apache/pmd`, `pmd-core`) was not fetched; findings rely on the documented XML schema and examples, which are internally consistent and XSD-referenced, but doc-only rather than source-verified.
- The Code Climate spec's own inconsistency between its worked example (`other_locations`) and its itemized field list (`trace`) was found in the primary spec file itself (`codeclimate/platform:spec/analyzers/SPEC.md`, ~lines 145-172) and is reported as-is, not resolved; GitLab's own "Code Quality report" doc page was not independently fetched to adjudicate it, only referenced via jscpd's code comment.
- SonarQube's `/api/duplications/show` response shape and Simian's output format were out of scope for this pass (one of either was to be picked per the brief; Code Climate/GitLab was chosen) and would need a follow-up fetch if the team wants them compared too.
