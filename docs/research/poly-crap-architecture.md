# Research note: transferable architecture practices from poly-crap

- **Source:** local reference repo `D:\Personal\poly-crap` (Rust CLI, "Find risky, untested complexity across polyglot codebases"), examined directly — source, tests, and first-party `docs/content/*.mdx`.
- **Scope:** engineering *practices* (crate layout, config layering, CLI/error/output/testing/release conventions). Not poly-dry's architecture — poly-dry's purpose differs; only patterns worth transplanting are flagged.
- **Citations** are `relative/path:line-range` against the poly-crap repo root.

## 1. Crate/module structure
`src/lib.rs:1-45` is a doc-comment that narrates the 5-stage pipeline (`config::load`/`EffectiveConfig` → `analyze_tree` → `parse_coverage_files` → `merge()` → `report::gate_entries`/`render_*`/`baseline::compare`), including a compiled `rust,no_run` doctest (`src/lib.rs:21-33`). It states explicitly: *"The JSON schemas in `schemas/` are the published contract; the Rust types here are not, and may change between minor versions"* (`src/lib.rs:41-42`), backed by versioned `schemas/report-v1.json` and `schemas/delta-v1.json`. Modules split cleanly along pipeline stages: `analysis.rs` (parse), `coverage.rs` (parse coverage), `merge.rs` (join), `report.rs` (gate/render), `baseline.rs`/`git_diff.rs` (diff features), `model.rs` (shared types), `config.rs` (config layering), `style.rs`/`table.rs` (presentation), `main.rs` (thin CLI shell).

**Adopt:** a `lib.rs` doc-comment that narrates the pipeline stage-by-stage with doc-links to the owning function/type, kept honest by a compiled doctest; declaring a versioned JSON Schema (not the Rust structs) as the actual stability contract for machine output.
**Don't copy:** the specific module boundaries — they're shaped by poly-crap's parse→score→report domain, not a general template.

## 2. Config layering (`src/config.rs`)
Three distinct types: `Config` (TOML file, all `Option`/empty-default fields, `#[serde(deny_unknown_fields, rename_all = "kebab-case")]`, `:55-58` — *"an unknown key is an error so a typo cannot silently do nothing"*), `Overrides` (CLI-sourced, `:103-123`, *"a caller sets only what it means to override"*), and `EffectiveConfig` (`:80-101`, fully resolved, non-`Option` — what the rest of the program consumes). `EffectiveConfig::new` (`:129-163`) applies a **per-field-category** merge rule, not one blanket rule: scalars are CLI-overrides-file-overrides-default (`cli.threshold.or(config.threshold).unwrap_or(DEFAULT_THRESHOLD)`); some lists *replace* wholesale if CLI set anything (`prefer_cli`, `:166-168`); other lists (`exclude`, `allow`) *join* file+CLI (`:135-139`); booleans are OR-merged via an `enabled()` helper (`:174-176`) so either source can turn on a gate. `DEFAULT_EXCLUDES` (`:9-50`) is a static baseline the layering can opt out of. The merge contract itself is pinned down by unit tests (`rejects_unknown_keys`, `overrides_win_over_the_file_and_lists_join`, ~`:204-260`).

**Adopt:** the 3-type split (file-only / CLI-only / resolved) with an explicit, *documented and tested* merge rule per field category (replace vs. join vs. OR vs. override-with-fallback); `deny_unknown_fields` on file config as a cheap typo guard.
**Don't copy / tradeoff:** hand-written field-by-field merge logic scales linearly with field count and already needs per-field commentary at ~15–20 fields (`:99-101`); past that, a declarative/macro approach or a layered-config crate (e.g. `figment`) trades poly-crap's explicitness for less boilerplate — a real choice to make deliberately, not default to.

## 3. CLI design (`src/main.rs`)
Single `#[derive(Parser)] struct Cli`, no subcommands — right-sized for a single-verb tool. Doc-comments on fields become `--help` text (e.g. `:61-63`), so help text isn't duplicated elsewhere. Mutual-exclusion/requirement constraints are expressed declaratively via clap attributes (`conflicts_with = "baseline"` at `:92`, `requires = "baseline"` at `:99`) rather than manual checks. `main()` (`:134-136`) only calls `parse_and_run`; all logic lives in library/free functions — `main.rs` is CLI plumbing over the `poly_crap` crate, never business logic itself. Exit codes are a 3-way map (`run_and_exit`, `:156-165`): gate-failed → 1, success → 0, runtime error → 2, documented in code and in `docs/content/08-reference/03-exit-codes.mdx`. Gating vs. display are two independently-named, explicitly-documented filter passes: `report::gate_entries` (`src/report.rs:103-112`, *"`--min` and `--top` are display limits and must not reach this set"*) decides the exit code; a separate `apply_display_limits` (`:118-127`) trims only what's printed, applied after gating.

**Adopt:** doc-comments-as-help-text; clap-declarative constraints over manual validation; thin `main()` delegating to a library crate; `ExitCode` (not `std::process::exit`) with a small, documented, stable exit-code contract; keeping "what decides success/failure" structurally separate from "what gets displayed" whenever both concepts exist independently.
**Don't copy:** the two-pass gate/display split is only worth it because poly-crap has independent `--min`/`--top`/`--allow` knobs — don't add the extra layer if a tool has only one filtering concept.

## 4. Error handling
`anyhow` is used exclusively across all of `src/*.rs` (no `thiserror`; confirmed absent from `Cargo.toml:21-33`). `.with_context(|| format!(...))` attaches **actionable**, not just descriptive, context at I/O/parse boundaries — e.g. `src/baseline.rs:51-56` tells the user to regenerate an older baseline on a stale-schema parse failure, not just "failed to parse." `bail!()` covers precondition failures with no underlying I/O error (`src/git_diff.rs:49-51`, rejecting a `--diff-base` value starting with `-`). The top-level handler prints the full context chain with `{error:#}` (`src/main.rs:162`), not just the top message.

**Adopt:** anyhow + mandatory context at failure boundaries, written as remediation hints; printing the full `{:#}` chain at the top level.
**Tradeoff:** anyhow-only means the library crate exposes no typed error enum — a caller can't `match` on error *kind* (config-parse vs. git-missing vs. ...) without string work. Fine for poly-crap's thin, CLI-first embedding surface; if poly-dry's library API needs callers to branch on error kind, that's a deliberate reason to use `thiserror` (or anyhow + downcasting) instead — not a default to inherit.

## 5. Output format strategy
One internal model (`Entry`/`MergeResult`) feeds three renderers (`OutputFormat::{Human,Json,Sarif}`, `src/report.rs:19-26`); format branching happens only at the render boundary, not deep in the pipeline. Format-dependent default filtering is data, not scattered conditionals: `RowFilter` (`:35-76`) — machine formats default to showing `All` entries ("so a JSON report can serve as a baseline", `:41-42`), human format defaults to `Failing(threshold)` (`:44-45`). Styling is architecturally fenced off from machine output: `style.rs:1-4` states *"the machine formats never see [a Theme], so JSON and SARIF cannot pick up an escape code by accident"*; only the human renderer's call signature accepts a `Theme` (`table::Table::render(theme, indent)`, `src/table.rs:91-110`), and JSON/SARIF builders serialize `Entry`/`DeltaEntry` directly via serde, never touching `table`/`style`. `table.rs` is a generic, domain-agnostic renderer (ANSI-aware width calc, `:113-124`; never-pad-last-column rule, `:144-152`). `style.rs` centralizes semantic color constants and resolves `ColorMode::{Auto,Always,Never}` honoring `NO_COLOR`/`CLICOLOR_FORCE` (`:48-84`); stdout/stderr themes are resolved independently (`src/main.rs:120-131`) so piping JSON to `jq` doesn't strip stderr warning color.

**Adopt:** single internal model, render-boundary-only format branching; default-filter-as-data per format; a hard rule (enforced by the renderer's type signature, not just convention) that color/style never reaches machine output; a generic table renderer kept separate from domain rendering; independent stdout/stderr color resolution.
**Don't copy:** SARIF is specific to static-analysis/code-scanning integrations (e.g. GitHub code scanning) — only relevant if a tool targets that ecosystem.

## 6. Testing strategy
Only two files under `tests/` (`cli.rs`, `git_diff.rs`), both black-box binary tests via `assert_cmd`. `tests/cli.rs:1-16` scrubs `NO_COLOR`/`CLICOLOR`/`CLICOLOR_FORCE` env vars so a developer's shell doesn't leak into assertions. `mixed_language_json_matches_schema` (`:24-82`) builds fixture sources + an LCOV file in a `tempfile::tempdir()`, runs the real binary, and validates stdout against the actual shipped `schemas/report-v1.json` via the `jsonschema` crate (`:78-82`) — the schema contract is tested against real output, not assumed in sync. `threshold_gate_and_config_precedence_work` (`:85-~110`) exercises CLI/file config precedence end-to-end, not just via `config.rs` unit tests. Pure logic is unit-tested in-module (`config.rs` merge semantics ~`:204-260`; `model.rs` Language parsing `:175-210`; `score.rs` CRAP formula tied to documented published examples `:11-18`; `table.rs` layout incl. a `#[should_panic]` case `:159-218`). `CONTRIBUTING.md:~78-81`: *"Tests must not require network access, private credentials, or changes to a developer's system"* — the git-subprocess tests comply by only exercising `git` against disposable tempdir repos they create themselves.

**Adopt:** pure logic unit-tested in-module, cross-cutting behavior black-box-tested via `assert_cmd`; validating machine output against the real shipped schema file rather than trusting serde stays in sync; an env-scrubbing test helper; real (not mocked) subprocess fixtures built in tempdirs.
**Caveat:** two integration files is a thin surface relative to module count (baseline+diff+multi-language+multi-coverage-format combinations aren't all covered) — copy the *testing style*, not "two files" as a target.

## 7. Extensibility pattern (languages)
`model.rs`'s `Language` enum is `#[repr(usize)]` with the comment *"The discriminant indexes parallel tables in `analysis.rs` and here, so the order is part of the contract"* (`src/model.rs:7-8`). One enum definition co-locates all per-variant metadata (`ALIASES`, `EXTENSIONS`, `NAMES` const arrays, `:24-56`) driving CLI parsing (`clap::ValueEnum`), serde, config parsing, and display — rather than scattering the same data as `match` arms across files. Grammar dispatch is a flat `match` (`src/analysis.rs:189-235`), not a trait or dynamic registry: adding a language means a new dependency + enum variant + match arm + const-array entries, all compile-time.

**Adopt:** co-locating per-variant metadata as const arrays on the enum when the variant set changes rarely (a deliberate, infrequent PR) — low indirection, one place to update.
**Don't copy:** this is a closed, compile-time-only extension point with no plugin system; it would not scale to runtime-pluggable behavior. The `#[repr(usize)]`-as-array-index contract is also a foot-gun — reordering variants silently breaks a *different* file's parallel array unless both files' comments are read.

## 8. Baseline/diff features
`baseline.rs` compares a current run to a saved JSON report via three successive tiers — `match_exact`, `match_suffixes`, `match_moves` (`:59-73`) — producing per-function `DeltaStatus::{New,Regressed,Improved,Unchanged,Moved}`, a fuzzy join tolerant of files/functions shifting between runs. `git_diff.rs` shells out to `git`, validates the base ref defensively (rejects values starting with `-` so they can't be misread as a flag, `:47-51`), resolves merge-base, and restricts analysis to changed line ranges. Both features are documented with an explicit statement of what they *don't* catch (`docs/content/06-gating/02-baselines.mdx`: *"`--fail-regression` ... says nothing about a `new` [function] ... so pair it with `--fail-above`"*) — gaps are called out in the docs rather than left for users to discover.

**Adopt (domain-neutral parts only):** tiered/fuzzy matching (exact → suffix → moved-detection) as a general strategy whenever comparing "current state" to "a prior saved state"; defensive rejection of flag-like strings before shelling out to a subprocess; documenting each gate's explicit blind spot next to its description.
**Don't copy:** "changed functions via git diff line-overlap, score the whole function if any line changed" is specific to poly-crap's complexity/coverage domain — not a concept to port, only the git-subprocess mechanics (merge-base resolution, path canonicalization) are domain-neutral.

## 9. Build/release tooling
`rust-toolchain.toml:1-4` pins an exact toolchain (not just an MSRV) plus `clippy`/`rustfmt`/`rust-analyzer` components, for CI/local parity. `dist-workspace.toml:1-19` configures `cargo-dist` for 6 targets with shell/PowerShell installers, and documents a deliberate quirk (`:17-18`: `allow-dirty = ["ci"]` because the generated CI workflow is hand-edited). `release-please-config.json` drives conventional-commits changelog/versioning (`release-type: "rust"`, draft releases, pre-1.0 minor-bump-on-breaking convention) and hides internal commit types from the user-facing changelog. `prek.toml:1-23` runs fast pre-commit-style hooks, including local `cargo fmt --check` / `cargo clippy -D warnings` / `cargo test`, each gated by a file-pattern (`:19-22`) so the full toolchain doesn't run on every commit regardless of what changed. `RELEASING.md` documents the full chain (release-please → tag → cargo-dist → crates.io) including a known GitHub Actions gotcha (tag-triggered workflows don't start from a token-created tag) and its workaround.

**Adopt:** the overall release-please + cargo-dist + prek stack as a mature, close-to-1:1-reusable reference architecture for a distributable Rust CLI (if poly-dry ships as one); pinning an exact toolchain version; a separate `[profile.dist]` so release-build settings don't slow local dev iteration; writing down known CI gotchas and their recovery procedure in a `RELEASING.md`, not just fixing them silently.
**Caveat:** the GITHUB_TOKEN/tag-workflow interaction is a known footgun specific to this exact tool combination — worth copying the *discipline of documenting it*, not necessarily the same workaround if poly-dry's CI differs.

## 10. First-party docs structure
`docs/content/` uses numeric-prefixed files/folders (`01-install.mdx` … `09-troubleshooting.mdx`) with a per-section `meta.ts` controlling nav order, built with the Blume docs framework (`pnpm --dir docs run build`/`validate` per `CONTRIBUTING.md`).

**Adopt:** numeric-prefix + per-directory ordering metadata as a portable, version-controlled doc-ordering convention, independent of doc-site generator.
**Don't copy:** the Blume/`meta.ts`/pnpm tooling itself — only relevant if poly-dry also adopts that framework.
